# 3DMk Capability Domain Implementation Sequence

## Purpose

Define the evidence-driven migration from current 3DMk behavior into a Veritas-child capability domain without weakening revision authority, CUDA-first execution, or standalone Tauri deployment.

The deterministic core is mandatory. The intelligence-escalation boundary is retained, but concrete embedded/local/cloud models are optional and cannot be production-enabled until their competence, cost, failure, and privacy behavior are measured.

## Phase 0 — Baseline and challenge audit

Before migration:

- inventory current import, analysis, mutation, VWM, reconstruction, measurement, save/reopen, package, and export behavior;
- map authority boundaries;
- record existing test/performance baselines;
- classify every proposed mechanism as `ESTABLISHED`, `VALIDATED`, `HYPOTHESIS`, or `RIFF`;
- remove `HYPOTHESIS`/`RIFF` material from normative requirements;
- attack high-confidence claims with countercases and boundary tests.

Exit: the operation being migrated has executable characterization evidence and no unsupported requirement is being smuggled in.

## Phase 1 — Upstream Veritas contract readiness

Before 3DMk implements a generic capability surface, verify that Veritas canonically owns the required contract.

Required upstream surfaces include, as needed:

- capability identity/envelope;
- typed state/effects/preconditions;
- execution/admission envelope;
- provider/resource envelope;
- provenance/checkpoint envelope;
- generic evaluation/convergence envelope;
- intelligence escalation/competence envelope;
- host/provider topology supporting approved in-process providers where justified.

If a generic surface is missing, add/version/validate it in Veritas first. Do not create a local substitute.

Exit: exact Veritas versions/fingerprints are pinned and the required generic contracts exist upstream.

## Phase 2 — Mechanical parent/drift enforcement

Implement:

- exact Veritas compatibility pin;
- contract-manifest fingerprint checks;
- thin 3DMk adapter boundary;
- dependency-cycle check proving Veritas does not depend on 3DMk;
- shadow-contract detector;
- compatibility failure tests.

Exit: migrated surfaces cannot build or run against incompatible Veritas contracts and no generic shadow contract exists locally.

## Phase 3 — Map one read-only operation

Wrap one low-risk existing geometry analysis capability using canonical Veritas contracts and geometry-specific metadata only.

Exit: direct legacy path and capability path are equivalent in result and provenance.

## Phase 4 — Explicit geometry state/composition

Define only geometry states and predicates required by migrated operations.

Exit: representative valid/invalid point-cloud and mesh compositions are rejected/admitted correctly without undocumented call order.

## Phase 5 — Deterministic planning/admission

Use the simplest bounded deterministic planner that meets current requirements.

Required: independent plan validation, explicit no-path result, reproducible ordering, hard constraints before preferences, and explicit search/resource budget.

Exit: no illegal or unregistered capability can be emitted or executed.

## Phase 6 — Sequencer/resource integration

Use canonical Veritas execution/resource primitives for dependency ordering, cancellation/failure propagation, resource requests, candidate staging, and provenance.

Exit: cycle, concurrency, cancellation, lock, resource-overcommit, and failure propagation tests pass.

## Phase 7 — Hardware provider integration

3DMk supplies geometry providers plus CUDA/Vulkan-WebGPU/CPU support declarations and cost/parity evidence. Veritas owns generic arbitration.

Exit: representative crossover, reserve, fallback, and correctness-parity tests pass.

## Phase 8 — Candidate mutation integration

Migrate mutating operations through `admit → stage → execute → validate → publish → finalize`.

Exit: fault injection at every boundary proves no partial authoritative revision and parent lineage/source mapping remain intact.

## Phase 9 — Geometry evaluators

Implement only independently verifiable metrics on fixed fixtures. Keep hard constraints, objective vectors, uncertainty/tolerance, and promotion evidence separate.

Exit: known-answer measurements reproduce within declared error bounds.

## Phase 10 — Latest/best/presented separation

Implement distinct latest, best, presented, and authoritative state identities.

Mandatory regression: candidate N is measurably superior to N+1; N remains incumbent after N+1 completes.

Exit: checkpoint/restart/rollback/provenance behavior passes.

## Phase 11 — Narrow deterministic convergence

Enable bounded iteration only for goals with measured benefit. Require explicit iteration/time/compute/memory budgets, incumbent retention, cancellation/restart safety, deterministic legality, and only the plateau/oscillation logic needed by the chosen strategy.

Exit: no infinite loop, lost incumbent, or hard-constraint bypass.

## Phase 12 — Intelligence escalation plumbing

Implement Veritas-owned typed escalation plumbing without requiring any model tier to exist.

First prove using deterministic stubs/fixtures:

- `RESOLVED` / `ABSTAINED` / `ESCALATE` / `FAILED` dispositions;
- deterministic escalation-package construction;
- schema-bounded return path;
- policy denial;
- stale-revision rejection;
- no authority bypass.

Only then may a concrete embedded/local/cloud provider be enabled after its own challenge-gate evidence.

Exit: disabling every probabilistic provider leaves deterministic core workflows intact.

## Phase 13 — Optional intelligence providers

For each proposed tier independently, benchmark the simplest candidate against the no-model baseline and declare accuracy/abstention, latency, memory, resource contention, privacy, malformed-output, and failure behavior.

No IA3, LoRA/xLoRA, RL, unsupervised adaptation, prompt optimizer, or specific model family is implied.

Exit: only providers with measured net benefit and bounded failure behavior are admitted.

## Phase 14 — Standalone Tauri integration

Package pinned required Veritas core components, the 3DMk child domain, and Tauri host as one product artifact.

Exit: clean Windows install, offline deterministic-core launch, representative import → capability → evaluate → save/reopen → export flow, and no separately installed Veritas application required.

## Phase 15 — Release closure

Run current 3DMk project-completion gates plus `NON_NEGOTIABLE_ACCEPTANCE_GATES.md` with evidence tied to exact commits/artifacts.

No capability-domain work is production-complete until all normative claims remain inside their validated error envelope.
